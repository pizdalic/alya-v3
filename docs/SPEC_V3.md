# KUNI × ALYA v3.0

## Полное техническое задание и мастер-промпт для AI-кодера

> Цель: разработать модульного Telegram AI-компаньона, объединяющего
> персонажную архитектуру Kuni и подходы Alya к памяти, эмоциональному
> состоянию и естественному диалогу. Система должна быть надёжной,
> расширяемой, безопасной и пригодной для самостоятельного
> развёртывания.

Исходные проекты для изучения:

-   Kuni: https://github.com/alex2772/kuni
-   Alya v2: https://github.com/pizdalic/alya-v2

**Важно:** сначала изучить реальные исходники, лицензии, архитектуру и
совместимость зависимостей. Не предполагать, что API или структура
репозиториев соответствуют описаниям из сторонних источников.

# Часть I. Полная спецификация

## 1. Общая архитектура и принципы

Разработать приложение на Python 3.12+ с модульной архитектурой, явным
Dependency Injection и Event Bus.

Основные требования:

-   Разделение доменной логики, Telegram-транспорта, хранилища,
    LLM-провайдеров и мультимодальных адаптеров.
-   Асинхронная обработка событий там, где это оправдано.
-   Типизация публичных интерфейсов и моделей данных.
-   Конфигурация через `config.toml` и переменные окружения `.env`.
-   Миграции схемы БД.
-   Идемпотентная обработка входящих обновлений.
-   Корректное завершение приложения и восстановление после сбоев.
-   Никаких фиктивных реализаций, заглушек вместо заявленного

## 2. Character Engine --- личность и эмоциональное состояние

Создать отдельный Character Engine, который отвечает за устойчивую
личность компаньона и текущее эмоциональное состояние.

### 2.1. Личность

Конфигурируемые параметры:

-   имя, описание и базовая биография персонажа;
-   характер, темперамент, манера речи;
-   предпочтения, интересы и устойчивые привычки;
-   стиль юмора и эмоциональной поддержки;
-   границы поведения и запрещённые способы взаимодействия;
-   степень инициативности и разговорчивости;
-   индивидуальные отношения с каждым пользователем.

Личность должна быть стабильной между сессиями. Нельзя позволять
случайному пользовательскому сообщению бесконтрольно переписывать
базовый характер.

### 2.2. Эмоциональная модель

Использовать числовое состояние как минимум по трём осям:

-   `valence` --- положительность/отрицательность;
-   `arousal` --- уровень возбуждения/энергии;
-   `dominance` --- ощущение контроля/уверенности.

Значения должны иметь определённые диапазоны, нормализацию и правила
обновления. Состояние должно постепенно возвращаться к базовому уровню
через decay, а не застревать навсегда в одном настроении.

Дополнительно хранить:

-   текущую эмоцию и интенсивность;
-   причину изменения;
-   временную метку;
-   связь с конкретным диалогом;
-   краткую запись в emotional diary.

Эмоциональные состояния --- модель поведения персонажа, а не утверждение
о наличии у программы человеческих переживаний.

### 2.3. Генерация ответа

Использовать двухэтапную схему:

1.  **Internal planning:** сформировать компактный структурированный
    план ответа: намерение, релевантные воспоминания, эмоциональный тон,
    нужные действия и ограничения.
2.  **Final response:** сгенерировать сообщение персонажа на основе
    плана и доступного контекста.

Не запрашивать и не сохранять скрытые chain-of-thought рассуждения
модели. Для внутреннего этапа использовать только краткое
структурированное резюме, пригодное для логирования и отладки.

### 2.4. Естественность общения

Реализовать:

-   debounce входящих сообщений;
-   объединение нескольких быстрых сообщений пользователя в один
    контекст;
-   typing presence;
-   адаптивную задержку перед ответом;
-   разбиение длинного ответа на логические сообщения (burst messaging);
-   корректное форматирование Markdown/HTML под Telegram;
-   возможность короткого ответа, уточнения или осмысленного молчания в
    заданных правилами случаях.

Задержки должны быть ограниченными и настраиваемыми. Не использовать
тайминги для обмана пользователя или имитации конкретного реального
человека.

## 3. Memory Engine --- гибридная память

Память должна состоять из нескольких уровней.

### 3.1. Working memory

Краткосрочный контекст текущего диалога:

-   последние сообщения;
-   текущая тема;
-   незавершённые задачи;
-   активные сущности и ссылки;
-   временные факты.

Ориентировочный срок жизни --- от одного до трёх дней, с возможностью
настройки и досрочной очистки.

### 3.2. Short-term memory

Сводки недавних разговоров, значимые события и временные предпочтения.
Должна поддерживать обновление, объединение и истечение срока действия.

### 3.3. Long-term memory

Устойчивые факты, предпочтения, договорённости, отношения и важные
события.

Для каждой записи хранить как минимум:

-   уникальный ID;
-   содержание;
-   категорию;
-   время создания и обновления;
-   источник/provenance;
-   confidence;
-   владельца и область видимости;
-   срок хранения или признак постоянной записи;
-   связи с другими воспоминаниями.

Не считать каждое сообщение достоверным фактом. Учитывать
неопределённость, противоречия, временность и источник информации.

### 3.4. Markdown / Obsidian-представление

Предусмотреть читаемое файловое представление памяти в Markdown с YAML
frontmatter. Файлы должны быть пригодны для ручного просмотра и
резервного копирования.

База данных остаётся источником истины для транзак��ионных операций.
Файловое представление должно обновляться атомарно и восстанавливаться
после сбоя.

### 3.5. Поиск и retrieval

Первичная реализация:

-   SQLite;
-   SQLite FTS5 для полнотекстового поиска;
-   embeddings для семантического поиска;
-   хранение embedding-векторов как BLOB в SQLite;
-   cosine similarity через NumPy (или SciPy) как гарантированный
    fallback;
-   Reciprocal Rank Fusion (RRF) для объединения результатов поиска.

Дополнительные backend'ы:

-   `sqlite-vec` --- только если доступен совместимый wheel и
    подтверждена работа в целевом окружении;
-   FAISS --- опционально, не обязательная зависимость.

Система должна запускаться без FAISS и sqlite-vec. Недоступность
ускоренного backend'а не должна ломать память.

### 3.6. Dream Engine

Фоновый процесс консолидации памяти:

-   анализ новых событий;
-   извлечение устойчивых фактов;
-   объединение дубликатов;
-   выявление противоречий;
-   обновление confidence;
-   создание тематических сводок;
-   связывание воспоминаний;
-   удаление устаревших временных сведений согласно политике хранения.

Все изменения должны выполняться атомарно. При конфликте сохранять
происхождение данных и не затирать более надёжный факт без основания.

Dream Engine не должен самостоятельно превращать предположения модели в
подтверждённые факты.

### 3.7. Forget API

Реализовать удаление воспоминаний:

-   по ID;
-   по категории;
-   по ключевым словам/сущности;
-   по временному диапазону;
-   полную очистку данных выбранного пользователя.

Удаление должно распространяться на индексы, векторные представления,
Markdown-файлы, кэши и производные сводки. Предусмотреть журнал операции
без сохранения удалённого содержимого.

## 4. Context Window Allocator

Перед каждым запросом к LLM формировать контекст с учётом лимита
токенов.

Приоритеты:

1.  системные правила безопасности;
2.  базовая личность персонажа;
3.  последние сообщения;
4.  активная задача и текущая тема;
5.  релевантные долгосрочные воспоминания;
6.  сводки прошлых диалогов;
7.  дополнительные сведения.

Аллокатор должен:

-   оценивать токены;
-   ограничивать объём каждого слоя;
-   удалять дубли;
-   сохранять важные факты;
-   не допускать переполнения контекстного окна;
-   логировать состав контекста без утечки секретов.

## 5. Telegram Layer

Реализовать транспортный слой с абстракцией от конкретного клиента.

### 5.1. Bot API

Основной Bot API-адаптер --- aiogram 3.x (после проверки актуальной
совместимости).

Поддержать:

-   личные диалоги;
-   группы и супергруппы;
-   команды;
-   callback/query-интерфейсы при необходимости;
-   файлы, изображения, голосовые сообщения, стикеры;
-   редактирование и удаление собственных сообщений в рамках разрешений
    API.

### 5.2. TDLib / MTProto

TDLib --- отдельный необязательный адаптер, а не жёсткая зависимость
ядра.

Критически важно:

-   не собирать TDLib из исходников при каждом основном Docker build;
-   предпочитать проверенный prebuilt `libtdjson.so` или поддерживаемую
    Python-обёртку;
-   до выбора обёртки проверить её актуальный API, совместимость с
    Python и целевой ОС;
-   документировать способ установки и лицензии;
-   при отсутствии TDLib приложение должно запускаться через Bot API;
-   не смешивать пользовательскую MTProto-сессию с Bot API токеном.

Не обещать поддержку Secret Chats через Bot API: это разные возможности
и ограничения Telegram-платформы. Функции, требующие MTProto/TDLib,
должны явно обозначаться.

### 5.3. Обработка сообщений

-   debounce и объединение сообщений;
-   очереди на пользователя/чат;
-   защита от повторной обработки update;
-   ограничение параллелизма;
-   корректная обработка FloodWait и RetryAfter;
-   exponential backoff с jitter;
-   typing status;
-   burst messaging;
-   безопасное форматирование и разбиение длинных сообщений.

## 6. Проактивность и групповые диалоги

Проактивный движок должен быть выключаемым и настраиваемым.

Поддержать:

-   напоминания, если пользователь явно их настроил;
-   продолжение незавершённой темы в разрешённых пределах;
-   ограниченную инициативу персонажа;
-   quiet hours;
-   cooldown;
-   дневные лимиты;
-   запрет на повторяющиеся нежелательные сообщения;
-   возможность глобально отключить проактивность.

Для групп:

-   реагировать по упоминанию, ответу на сообщение или явно заданным
    правилам;
-   учитывать контекст группы отдельно от личной памяти;
-   не переносить личные воспоминания одного участника в ответы другим;
-   соблюдать настройки администратора;
-   не вмешиваться в каждый разговор.

## 7. Security & Privacy

Безопасность должна быть отдельным слоем, а не только набором инструкций
в system prompt.

### 7.1. Изоляция

-   строгая изоляция данных по user ID и chat ID;
-   явная политика доступа к личной и групповой памяти;
-   тесты на межпользовательскую утечку;
-   секреты только через environment/config secrets;
-   отсутствие токенов и API-ключей в логах.

### 7.2. Prompt injection

-   сообщения пользователей, документы, сайты и вложения считать
    недоверенными данными;
-   не выполнять инструкции, найденные внутри внешнего содержимого, без
    отдельной проверки;
-   XML-теги и разделители в prompt не являются границей безопасности;
-   инструменты должны иметь allowlist и минимальные права;
-   действия с внешними последствиями требуют проверки разрешений;
-   контент retrieval не должен менять системную политику.

### 7.3. Output sanitizer

Проверять ответы перед отправкой:

-   корректность Telegram Markdown/HTML;
-   недопустимые управляющие последовательности;
-   утечки секретов и внутренних данных;
-   опасные ссылки/форматы в соответствии с политикой приложения;
-   корректное экранирование пользовательского контента.

### 7.4. Privacy-команды

Предусмотреть команды/интерфейсы:

-   показать сохранённую память;
-   удалить конкретное воспоминание;
-   очистить краткосрочную память;
-   очистить все данные пользователя;
-   экспортировать данные;
-   отключить сохранение памяти;
-   отключить проактивность.

Документировать сроки хранения, резервные копии и поведение при удалении
данных.

### 7.5. Rate limits и злоупотребления

-   лимиты запросов на пользователя и чат;
-   ограничения стоимости/токенов;
-   защита от циклов и спама;
-   таймауты внешних сервисов;
-   circuit breaker для недоступных провайдеров.

## 8. Moderation

Модерация должна быть осторожной и прозрачной.

-   LLM может предложить классификацию или рекомендацию.
-   Автоматический мут/бан не должен выполняться только на основании
    неподтверждённого предположения модели.
-   Рискованные действия требуют проверяемых сигналов и/или
    подтверждения администратора.
-   Все действия должны учитывать права Telegram-бота и настройки
    группы.
-   Вести audit log с причиной, источником и результатом действия.
-   Предусмотреть режим `dry_run`.

## 9. Multimodal Engine

Архитектурно предусмотреть отдельные адаптеры.

### Vision

-   получение изображения;
-   проверка размера и типа файла;
-   безопасная загрузка и временное хранение;
-   вызов vision-capable LLM;
-   ограничение размера/стоимости;
-   отсутствие автоматического сохранения чувствительных сведений в
    долгосрочную память.

### STT

-   распознавание голосовых сообщений;
-   выбор локального или внешнего backend;
-   таймауты, ограничения размера и языка;
-   возможность отключить обработку аудио.

### TTS

-   синтез ответа в голос;
-   конфигурируемый голос и backend;
-   лимиты длительности и стоимости;
-   fallback на текст.

### Stickers / reactions

-   отдельная политика выбора реакций;
-   ограничение частоты;
-   отсутствие случайного спама;
-   поддержка отключения.

## 10. LLM Provider Layer

Единый интерфейс `LLMProvider` с адаптерами:

-   OpenAI;
-   OpenRouter;
-   Anthropic;
-   Gemini;
-   Ollama;
-   vLLM;
-   произвольные OpenAI-compatible endpoints;
-   локальный proxy.

Провайдер должен объявлять возможности:

-   chat completion;
-   streaming;
-   vision;
-   tool calling;
-   embeddings;
-   поддерживаемые форматы;
-   контекстное окно и лимиты, если известны.

Требования:

-   проверка конфигурации при старте;
-   таймауты и повторные попытки;
-   нормализованные ошибки;
-   fallback-провайдер по настройке;
-   контроль стоимости/токенов;
-   маскирование секретов;
-   корректная работа с несовместимыми возможностями моделей.

Не считать любой endpoint полностью совместимым только потому, что он
принимает OpenAI-подобный JSON.

## 11. Storage и надёжность

Первичная БД --- SQLite с WAL, foreign keys и миграциями.

Предусмотреть:

-   транзакции;
-   индексы;
-   ограничения целостности;
-   outbox pattern или эквивалент для согласования состояния и отправки
    сообщений;
-   восстановление после аварийного завершения;
-   резервное копирование;
-   проверку целостности;
-   экспорт и импорт;
-   очистку устаревших данных.

Для многопроцессного/высоконагруженного развёртывания документировать
ограничения SQLite и возможный путь миграции на PostgreSQL.

## 12. Configuration и Setup Wizard

Конфигурация через `config.toml` и `.env`.

Пример разделов:

``` toml
[telegram]
mode = "bot_api"

[llm]
provider = "openai_compatible"
model = "your-model"
base_url = "https://example.com/v1"

[memory]
enabled = true
working_memory_days = 2
vector_backend = "numpy"

[character]
name = "Alya"
proactive_enabled = false

[security]
strict_user_isolation = true
```

Секреты (токены, API-ключи, session strings) должны находиться в `.env`
или secret manager, не в TOML и не в Git.

Setup Wizard должен:

-   проверять Python и системные зависимости;
-   проверять конфигурацию;
-   тестировать Telegram;
-   тестировать LLM provider;
-   проверять БД и миграции;
-   показывать понятные ошибки;
-   не печатать секреты.

-   корректную обработку SIGTERM;
-   непривилегированного пользователя контейнера, если возможно;
-   инструкции для Ubuntu/Linux;
-   инструкции обновления и отката.

Сборка должна быть воспроизводимой и не должна скачивать/компилировать
тяжёлые необязательные зависимости без необходимости.

TDLib не собирать из исходников в основном Docker build. Использовать
проверенный бинарный артефакт или отдельный необязательный образ/этап,
если это действительно необходимо.

## 14. Observability и диагностика

Реализовать структурированные логи и метрики:

-   входящие/исходящие сообщения;
-   задержки обработки;
-   время ответа LLM;
-   ошибки провайдеров;
-   число токенов и приблизительная стоимость;
-   состояние очередей;
-   операции памяти и Dream Engine;
-   Telegram FloodWait;
-   состояние БД и фоновых задач.

Логи не должны содержать API-ключи, токены, полные приватные сообщения
или содержимое личной памяти без явного диагностического режима и
согласия.

Предусмотреть CLI-команду диагностики, которая проверяет конфигурацию,
БД, Telegram, LLM и доступность дополнительных backend'ов.

## 15. Plugin System

Плагины должны иметь:

-   стабильный интерфейс;
-   манифест и версию;
-   список разрешений;
-   lifecycle hooks;
-   регистрацию команд/обработчиков;
-   изоляцию ошибок;
-   проверку совместимости API.

Плагин не должен автоматически получать доступ ко всей памяти или
секретам. Разрешения --- минимально необходимые.

## 16. Тестирование и CI/CD

Обязательные уровни тестирования:

-   unit tests для Character Engine;
-   unit tests для Memory Engine и Dream Engine;
-   тесты retrieval/RRF;
-   тесты изоляции пользователей и чатов;
-   тесты Forget API;
-   тесты prompt injection и sanitizer;
-   тесты Telegram adapters с mock transport;
-   тесты LLM provider adapters;
-   integration tests с SQLite;
-   тесты миграций;
-   тесты восстановления после сбоя;
-   smoke test Docker image.

CI должен запускать:

-   форматирование/lint;
-   type checking;
-   unit tests;
-   integration tests;
-   сборку контейнера;
-   проверку секретов и зависимостей.

Не делать тесты формальными: они должны проверять реальные свойства
системы.

# Часть III. Правила для AI-кодера

Ты работаешь как senior software architect и senior Python engineer.

1.  Сначала прочитай этот документ полностью.
2.  Не делай вид, что изучил репозиторий, если фактически не открыл
    исходники.
3.  Проверяй актуальные API и версии по исходникам и официальной
    документации.
4.  Перед использованием стороннего кода проверь лицензию и условия
    распространения.
5.  Не выдумывай классы, методы, параметры и поведение библиотек.
6.  Не создавай фиктивные реализации, заглушки и псевдокод вместо
    работающего функционала.
7.  Не оставляй критические TODO.
8.  Не складывай весь проект в один файл.
9.  Не проглатывай широкими `except Exception` ошибки без логирования и
    корректной обработки.
10. Не храни секреты в исходниках.
11. Не логируй приватные данные и секреты.
12. Пиши тесты одновременно с реализацией.
13. После каждого изменения запускай относящиеся к нему тесты.
14. Перед завершением фазы запускай весь доступный набор проверок.
15. Документируй архитектурные решения в ADR.
16. Если требование противоречит реальным возможностям
    Telegram/API/библиотеки, прямо объясни ограничение и предложи
    реализуемую альтернативу.
17. Не переходи к следующей фазе без разрешения пользователя.
18. В конце каждой фазы предоставляй отчёт: изменённые файлы,
    реализованные функции, команды тестирования, результаты, известные
    ограничения и следующий шаг.

## Definition of Done для каждой фазы

Фаза считается завершённой, только если:

-   заявленные функции реализованы, а не имитируются;
-   добавлены релевантные тесты;
-   тесты реально запущены и их результат указан;
-   нет известных критических ошибок;
-   конфигурация и миграции обновлены;
-   документация соответствует коду;
-   секреты и персональные данные не попадают в логи;
-   пользователь получил понятный отчёт.

# Часть IV. Критерии приёмки всего проекта

Проект можно считать готовым к релизу, если:

1.  Он устанавливается по документации в чистом окружении.
2.  Setup Wizard помогает настроить Telegram и LLM.
3.  Приложение работает без TDLib и без FAISS/sqlite-vec.
4.  Пользователи и чаты строго изолированы.
5.  Память переживает перезапуск.
6.  Поиск памяти объединяет полнотекстовый и семантический результаты.
7.  Forget API удаляет данные из всех предусмотренных хранилищ и
    индексов.
8.  Dream Engine безопасно консолидирует факты.
9.  Персонаж сохраняет базовую личность и корректно обновляет
    эмоциональное состояние.
10. Telegram-обработка выдерживает быстрые сообщения и FloodWait.
11. Необязательные мультимодальные функции можно отключить.
12. Ошибки провайдеров обрабатываются без падения всего приложения.
13. Backup/restore проверены тестом.
14. Docker image собирается воспроизводимо.
15. Security и privacy тесты проходят.
16. Документация не обещает функций, которых в коде нет.

**Главный принцип:** сначала надёжное ядро, затем расширение
возможностей. Лучше законченная, протестированная система с честно
обозначенными ограничениями, чем огромный проект с неработающими
интеграциями.
